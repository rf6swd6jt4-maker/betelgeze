## Scope and behavior

The latest “Assess platform consolidation” message proposed queue refresh, Appointment Setting access correction, an admin transfer with preview/reason/audit/retry, and real staff acceptance. The earlier choice was bookings **and** GHL setup. Existing Appointment Setting pages intentionally redirect to Client Connections; this candidate preserves those redirects. Restoring a booking screen is outside this change. Backend booking authorization does not establish that a staff user can reach a booking screen.

An owner/admin opens Relationships → a relationship → a service in Onboarding, Setup or Maintenance → **Transfer assignee**. Eligible people and the exact work preview load only on demand. Shared, completed, archived, private and service-group work cannot be selected. Exclusively linked open work can move; unrelated explicit owners/collaborators require selection rather than being selected by default. Work with no explicit owner or collaborators must follow the service responsibility. At most 200 linked records are admitted; larger services stop with a bulk-review message, never a partial transfer.

The admin reviews retained ownership/access and supplies a reason. A single transaction rechecks the current preview fingerprint under locks, changes the versioned service responsibility, changes only selected execution owners, removes only the former service assignee from those selected work collaborator lists, verifies recipient work access/queue ownership and applicable booking/setup permission, and stores an immutable receipt. Other collaborators remain. Sales, completed work, onboarding snapshots, billing and files are preserved. The existing Team membership rule adds the recipient and retains existing members; message reads, unread rules and delivery behavior are unchanged.

Retaining an explicit work owner is not a promise that they retain service-derived access. The dialog discloses this before acknowledgement. Retained setup/booking indicators follow the same eligibility, role, template and stage rules as the actual permission checks, excluding the transferred instance. Independent setup grants are preserved.

Before dispatch the dialog checkpoints its bounded exact request and named preview through the existing account/workspace/service-scoped draft journal. Storage failure prevents dispatch. An uncertain result freezes the payload; retry uses the same request ID. Reopening offers explicit recovery/retry, never automatic replay. Malformed or differently scoped journals cannot be rendered or replayed. A committed receipt is shown before the initiating service refresh.

After a service is completed, paused or cancelled, its detail still offers **Review saved transfers** to owners/admins. This mode performs no eligible-person or preview reads and cannot start a new transfer. It retries only the exact saved request to recover an existing receipt; a missing receipt is rejected by the current lifecycle check.

## Existing owners and performance

- Service identity/version/audit: `change_service_instance`, `guard_service_instance`, immutable stage events. The transfer does not enter the SOP generation wrapper.
- Work access: `workspace_user_can_access_work_item`, `personal_queue_owns`, existing owner/assignee triggers. Recipient access is checked before commit.
- Setup: existing GHL connection command retains its secrets, leases and provider behavior; only permission predicates change.
- Bookings: current delivery service assignments override obsolete legacy attribution. Draft/submit commands drop only their redundant relationship-wide Retention condition. Legacy assignments remain usable where no delivery instance exists and their legacy conditions hold; a tentative negotiating/declined/deferred/unpaid opportunity does not revoke them. Once delivery responsibility exists, paused/cancelled/completed states cannot revive a stale legacy assignee. When a client has several authorized Appointment Setting services, the reader preserves the earliest legacy assignment choice and uses a deterministic fallback only for current-only assignments.
- UI: shared CenteredDialog, AssignmentSelector, DetailFields and List; lazy dialog chunk; existing mutation/departure/journal owners. No new ordinary-tab polling or provider calls.
- Conflicting edits: the new transfer acquires its service instance with NOWAIT and converts lock/deadlock failures into known rollback conflicts. A timeout before receipt serialization remains uncertain and must retry the same request. The canonical service-change command is unchanged. Injected late database errors prove rollback of the transfer attempt; real multi-session PostgreSQL interleavings and competing-writer outcomes remain unverified. The shared-command lock-order experiment is held outside installable migrations because it added measured replay work.

### Shell setup permission — reuse existing eligibility

The rejected experiment replaced the existing exact setup-assignee lookup on routine shell authorization with a service-derived helper. Indexed synthetic PostgreSQL/WASM measurements found extra database work. At 100,000 service instances, with 1,000 non-Appointment-Setting assignments for the denied staff actor, the check measured about **1.722 ms per call** versus approximately **0.002 ms** for the prior explicit-grant lookup. The explicit-grant case also measured about **0.251 ms**. These are batch-average local database observations, not production shell latency. Reproduce the rejected comparison with `scripts/benchmark-service-setup-access.mjs`; exact results and the largest denied-query plan are retained in `setup-check-benchmark.jsonl`.

The user selected the alternative that removes those joined service/revision/eligibility probes from routine shell loads. The transfer migration leaves `workspace_shell_bootstrap` unchanged; the application reuses its returned Appointment Setting capability. The fallback retains its original indexed explicit setup-assignee lookup and reuses the Appointment Setting eligibility it already loaded. No new shell database request or service-instance scan is required.

Eligibility exposes the Client Connections panel; exact relationship authorization remains in its list and connection command. An eligible unassigned staff member can see an empty panel, but receives no client rows, credentials or connection-command access. Independent setup grants remain valid. The transfer SQL fixture checks the unchanged shell definition and denies former/unassigned staff across list, connect, refresh, finish and failure commands.

The connection action now allowlists its credential/target fields and always obtains workspace and actor identity from the authenticated context. A runtime regression reproduced the previous spread-input override, including reaching a stubbed provider as another actor; forged extra identity fields can no longer override that context or pass the exact client grant.

The list implementation also avoids calling an opaque permission helper once for every eligible client. That rejected shape repeated 2,000 helper/relationship loops and 19,105 shared buffer hits for a denied staff actor at 2,500 relationships/10,000 service instances. The final staff branch starts from the actor's current assignments and independent setup grants through existing indexes; the same denied plan needs three buffer hits. It reuses the original list projection and leaves the owner/admin list and provider/lease implementation intact. Existing explicit command grants retain their original fast path; a new service-derived grant uses one scoped check.

Eleven warmed alternating PostgreSQL/WASM EXPLAIN observations at that population measured median database execution time (baseline → final): explicit setup grant **3.327 → 0.648 ms**, denied staff **3.136 → 0.522 ms**, and owner **10.693 → 10.675 ms** with identical rows. Newly permitted derived staff received 100 rows in **1.493 ms**; its former zero-row response is not an equivalent user outcome. The rejected helper shape took about **460–470 ms** for those staff cohorts. These isolated timings exclude network, provider delivery, production concurrency and physical devices; they do not establish end-to-end speed.

The actual migration installer was then executed independently: its staff list branch is byte-identical to the measured query, its owner/admin projection is unchanged, and its command tail differs only by the reviewed explicit-or-derived grant. Exact JSON comparisons cover state/grant combinations, roles, independent setup assignments, legacy rows, tentative opportunities, revoked eligibility and inactive workspaces. The timed fixture has a minimal schema with existing index key shapes and current-instance growth; its legacy allocation table is empty during timing, with legacy grants checked functionally. Reproduction: `scripts/benchmark-client-connection-list-access.mjs`; retained evidence: `client-list-benchmark.jsonl`. The timed list branch is unchanged by the final compatibility fixes. Final transfer migration SHA-256: `423191525452ae60180a9713d8730ca49dde7743b7e367fdbc8cce4e172a7647`.

### Step 1: queue refresh — investigated, automatic repair held

`20260914180000_relationship_queue_presentation.sql` replaced `read_relationship_work_queue` without its generation metadata. The existing `useSopWorkRefresh` therefore cannot see pending generation. An already-open admin queue can remain empty after publication.

The isolated repair prototype restores ten bounded generation reports through the existing request/run indexes. At 20,010 synthetic requests, the plan reads ten request rows and at most ten run primary-key probes. Forty alternating samples per arm measured median **1.278 → 1.369 ms**, p95 **1.361 → 1.429 ms**, and **1,847 additional JSON bytes**. Staff and later-page controls overlap. This is a measured added read cost, not a production latency result.

Restoration also reactivates existing automatic progress dialogs and overlapping queue/progress polling. Generation is absent for staff and later pages. Reports can be marked presented before the parent accepts opening them. These limitations mean the prototype is not a complete refresh solution.

`queue-refresh-prototype.sql` remains outside `supabase/migrations`; it is an uninstalled experiment, not a release migration. The user selected an on-demand Refresh queue control through the current authorized queue endpoint, without restoring generation metadata or automatic queue polling.

The control uses the existing visible queue reader and current page. It keeps rows, scroll and unrelated drafts while refreshing, coalesces repeated clicks and retains rows on transient failures. Access-loss responses clear private rows; account/destination changes discard the old queue owner and late responses. Service publication and existing Gantt invalidation remain available; the dormant queue polling hook is removed. No routine request, SQL payload or navigation is added.

### Assignee-transfer chat cleanup — 5 November 2026, local validation

A production report (transferring a client's Google Ads service to a new assignee) found the former assignee still a member of the client's Team chat afterward. Investigation confirmed `transfer_service_assignee` only ever updated `relationship_service_instances.assignee_user_id` and reassigned selected work items; the two triggers reacting to that column change were either purely additive (`sync_service_fulfilment_chat` → `ensure_active_service_fulfilment_chat`) or gated on the opt-in Shared Service Assignees roster already existing for that instance (`sync_service_queue_lifecycle`, a no-op for an ordinary single-assignee transfer). The preview's `teamMembershipRetained` field was also a hardcoded `true`, never computed.

The user explicitly authorized closing this gap: re-evaluate the former assignee against the same eligibility the Shared Service Assignees feature already uses for its own chat sweep, but scoped to only the one person just replaced.

`supabase/migrations/20261105120000_service_assignee_transfer_chat_cleanup.sql` adds `service_assignee_chat_membership_justified(workspace, relationship, user, exclude_instance default null)` — a direct generalization of `sync_service_queue_chat`'s existing four-clause eligibility chain (shared-queue membership, primary assignee of another active onboarding/setup/maintenance instance, legacy `relationship_services` assignee, seller/fulfilment-manager), minus its `service_queue_chat_members` tag join since this checks one named user rather than sweeping a tagged roster. `preview_service_assignee_transfer` calls it (excluding the instance being transferred) to compute a real `teamMembershipRetained`, mirroring the existing `formerSetupRetained`/`formerBookingRetained` instance-exclusion pattern. `transfer_service_assignee` calls it immediately after `change_service_instance` commits the new assignee and, only if ineligible, deletes the former assignee's one `workspace_team_members` row for that relationship's team (plus a defensive, normally-no-op cleanup of any `service_queue_chat_members` tag). No new trigger is added; the Shared Service Assignees feature's own "promotion to primary retains historical grant" rule for its internal roster/lifecycle path is a separate code path and is unchanged.

`ServiceTransferDialog.tsx` now shows the admin which outcome will happen, branching on the real `teamMembershipRetained` value instead of the previous unconditional "members remain members" copy.
