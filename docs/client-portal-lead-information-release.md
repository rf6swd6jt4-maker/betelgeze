# Client portal lead information and unified appointment entry

## Scope and ownership

Base: `66a5522ba21f344cd5d10f77b5eac2e327387b95`. Candidate branch: `codex/portal-lead-information`. User authorized implementation and deployment, full portal access from notification links, and the disclosed additional cold notification startup work. No new appointment, test notification, message resend, credential change or Meta account change is part of this release.

Both ordinary portal and notification routes use the same server entry and `ClientPortalShell`. Notification loading uses the same startup component and public agency logo without passing an appointment capability to a session endpoint; its brief loading background remains neutral until the full portal theme arrives. Link-preview metadata remains generic to avoid publishing appointment/contact information. An existing notification capability resolves its currently active portal session through the existing exact workspace/relationship/hostname/fingerprint checks, then opens its already-read appointment in the full portal. It does not redirect, mint a new capability or rewrite WhatsApp links. With the approved full-portal grant, opening a notification makes the existing portal credential available to that browser just like an ordinary portal link. Revoking only one appointment link cannot revoke a portal credential already disclosed; revoke/reissue the portal session to revoke that full access. Calendar clicks and notification entry use the same appointment presentation. Back to calendar stays inside the same portal and preserves the calendar state.

## Retained lead information

The existing GHL contact response supplies source, contact type and explicitly mapped custom fields. No new provider request or interactive provider lookup is added: the adapter still makes its existing four reads. A profile's new bounded `lead_field_mapping` selects at most eight exact field IDs and reviewed question labels; no other custom fields or arbitrary provider objects enter client responses. Current contact information is labelled as such, not represented as verified original booking answers.

The initial Jason mapping uses the two questions verified against the supplied screenshot and actual contact payload: home ownership and product interest. Generic mapping storage supports future clients; a field-picker/setup UI and automatic label discovery are deferred. Automatic discovery requires the location custom-fields read scope, which the audited connection did not have. Each future client needs a reviewed mapping for that client's GHL fields; IDs must not be copied between unrelated locations. Existing profile reconfiguration preserves its mapping. A newly selected calendar or location creates a separate profile with no mapped questions until reviewed; no historical mapping is silently copied.

Bounds: labels 200 characters, values 1,000 characters, eight fields, at most 256 source custom fields and 20 scalar values in an array. Unsupported object values and over-limit data are omitted rather than serialized. These limits do not promise full raw CRM retention. The public summary has an explicit allowlist, and internal notes remain outside it.

Lead-only refresh updates the latest retained snapshot without producing lifecycle versions or notices. Existing appointment versions, outbox snapshots, message bodies and button evidence remain immutable. Old workers omitting the new field retain it only for the same contact; explicit null clears it, and contact identity changes cannot inherit another lead's data. A capture-time fence protects against out-of-order contact reads. Existing polling/queue timing applies; no new instant-update guarantee is made. Portal-only ContactUpdate fanout is unchanged in this basic release.

## Speed and validation

The additional full portal startup on notification entry is explicitly authorized in `app_speed.md`. Source-level counts are logical database operations, not network latency measurements. Normal portal loading order remains unchanged. Seeded notification entry avoids a repeated appointment detail read; the calendar is fetched on return rather than while details are open. Visited views retain their existing mounted state.

The mapping uses a private checked JSON domain so assignment validates the bounded mapping while routine profile lease/bookkeeping updates do not revalidate it. Historical migrations remain unchanged. `20261026010000_ghl_appointment_lead_fields.sql` is the only new migration.

Local validation: 1,837/1,837 unit tests; production webpack build; historical migration/changed-file lint gate; 970/970 browser Foundations assertions across 48 fixtures; 28 integrated portal navigation cases, 66 summary/lead cases and six calendar engine/viewport scenarios. Chromium and WebKit are both covered. Integrated cases include identical details from both entries, no duplicate seeded reads, selected time-zone day/month, scroll/cache restoration, inactive work, changed calendar, revoked session, and returning to the current empty or native-appointment mode. The initial maximum-payload fixture exceeded the pre-existing title/name input bounds; correcting that fixture and rerunning passed. Browser screenshots were inspected. Physical phones are not covered.

The complete disposable native PostgreSQL suite passes authorization, profile lifecycle, history/version/outbox preservation, stale/invalid capture ordering, contact/revision changes and equivalent core-change classification. The final migration also replaces four sequential JSON-key removals in the existing equality lane with one equivalent array-key removal, avoiding intermediate rich-detail copies. In the final quiet isolated PostgreSQL 18 run (90 paired samples per path), lead-only processing median/p95 was 0.525/0.627 to 0.507/0.574 ms; legacy processing was 0.406/0.453 to 0.393/0.453 ms. Paired median lead difference was -0.013 ms with bootstrap interval [-0.023,-0.009]; legacy -0.005 with interval [-0.018,+0.003]. Earlier fence-only variants had extra cost and were replaced. Separate 25,000-row profile fixtures detected no median bookkeeping regression from the mapping domain. These are synthetic database execution observations, not production latency promises.

Exact candidate SHA, hosted CI, migration installation, Vercel status and bounded live results are recorded on the release PR and in the task handoff; they are separate from local validation. Production checks must be bounded read-only inspections of existing records and links, with no generated messages, uploads or appointments. Synthetic browser checks and physical device confirmation are distinct.
