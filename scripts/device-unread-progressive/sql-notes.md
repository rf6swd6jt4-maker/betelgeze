# Isolated SQL diagnostic provenance and limits

These scripts are diagnostics, not application changes or installable release migrations. `sql-held-device.sql` retains held candidate `cdaa9f7f` as fixture source only; no production database is connected. `sql-base.mjs` loads canonical historical helpers/read summaries from the worktree and the latest shared read optimization `20261010120000_communication_read_efficiency.sql`. The only additional function is a bounded authorized preview/cursor batch in `sql-preview.sql`.

`BE_PGLITE_ROOT=/private/tmp/be-device-redesign-pglite node scripts/device-unread-progressive/sql-measure.mjs PATH` runs the main isolated measurement/24-assertion pack. `sql-supplement.mjs PATH` measures fresh storage, Client bounded2000 projection, fresh new-installation initialization, matched account-ahead summaries, and uncontended large-chat summary/preview comparisons. `sql-behavior.mjs PATH` verifies first-installation policies, revoked access and rollback. All use fresh in-memory PostgreSQL/PGlite and synthetic 120-byte plaintext bodies; no connection URL is accepted.

Each dataset's `chats` is TOTAL conversations, half Client and half Native direct conversations. `devices` is initialized retained scopes, not the total known inventory. A backlog 100 cohort contains 101 messages/chat with the first acknowledged; backlog 0 contains one acknowledged message. Counts cap at 100, corresponding to the UI 99+ badge. The 20-total-chat backlog 10,000 cohort contains 200,020 messages in total.

Main timings: 30 observations / 5 warmups for reads/initialization; 60 observations / 8 warmups with restored state and alternating baseline/candidate order for cursor mutations. Independent read arms alternate execution order. `sqlMs` is PostgreSQL EXPLAIN ANALYZE Execution Time; `wallMs` adds the WASM bridge and explain-result parsing, not HTTP/body transfer. Payload bytes are UTF-8 JSON serialization of the fixture result. Failures 0 applies to the completed measurement pack: an earlier whole-pack attempt failed after measurement because its diagnostic write-count trigger lacked a schema qualifier under the function's empty search_path; the fixture was corrected and the full pack rerun.

The first 1000-chat main cohort overlapped briefly with a WebKit correctness fixture; use the supplement's uncontended repeated summary/preview comparisons for conclusions about that cohort. Treat other 1000-chat timings as exploratory rather than a production ceiling. Main storage sizes include initialization churn; use supplement `freshStorage` for growth comparisons.

## Baseline and index fidelity

The Native baseline executes current `communication_native_inbox`: one preview per authorized conversation plus its per-unread-message identity metadata. Its bounded-message helper is a synthetic plaintext projection; production decrypt/sign/attachment CPU is excluded. Client baseline returns the current global recent 2000-row projection plus explicit account cursors, also without decryption. These reduced fixtures are not full Next.js route builds, native Supabase network runs, portal fixtures or production latency.

Native message primary key, `(workspace_id,id)` uniqueness and `(conversation_id,created_at desc)` index match the current read-relevant repository schema (`20260815143000_workspace_teams_native_chat.sql`). The Client fixture includes message primary key, `(workspace_id,created_at desc)` and `(relationship_id,created_at desc)` indexes matching `20260814200000_communications_workspace.sql` / `20260710100000_canonical_relationships_assets.sql`. It omits provider/contact/reply indexes and their columns, notably `relationship_contact_recent_inbound`, `relationship_contact_latest_message` (`20260913120000_relationship_card_workspace.sql`) and `client_messages_staff_reply_recent` (`20260919083000_relationship_engagement.sql`). Client timings do not represent the complete production index inventory. Message-encryption, push and other production insert/update triggers are absent. No message mutation throughput claim is made.

Latest canonical authorization helper definitions are reused: AAL2/workspace member from `20260821120000_account_system_v2.sql`; native readable from `20260821150000_encrypted_communications.sql`; Client access from `20260909100000_client_delivery_teams.sql`. The synthetic schema has one staff member, direct-conversation memberships and seller-owned Client relationships, not the full variety/cardinality of production membership, resolver, system-message and portal cases.

## Interpretation boundaries

- Invoked-RPC duplicate/account-ahead timings do not replace the current browser's zero-request baseline. A newly observed device position can require an additional acknowledged request where the shared account needs none.
- An advancing device read changes one private device cursor and, only if needed, one shared cursor. A device-only catchup changes no shared row. Repeated/older calls change no row. Trigger counts are changed rows, not WAL, lock or CPU counts.
- All device tables are private and omitted from realtime publication. Account cursor/read/push functions retain current account-wide behavior. This fixture tests cursor effects; it cannot establish actual push-provider delivery.
- `cursorKnown:true,deviceCursor:null` is confirmed absence from a successful authorized batch. Before that response or on failure, the client must retain unknown/pending state. Full timestamp/UUID positions survive message deletion. Bound batches have 1–20 requested IDs; the eventual endpoint should deduplicate before calling.
- Per-device summary responses omit the full cursor map but still aggregate all authorized conversations. Preview bodies and cursor recovery use batches of 20. Large unread backlog does not require downloading all message IDs/bodies in the candidate.
- First-time initialization still copies O(conversations) cursor rows; retained storage grows O(conversations × initialized installations). The global cutover freezes all account cursors/known installation inventory; production cardinality, cutover lock/WAL duration and concurrent initialization remain unmeasured.
- A known installation uses the frozen cutover boundary. A new installation, including an old browser that has lost its installation identity, seeds current shared account positions. That reset policy needs explicit product approval; retaining the cookie while losing local cache can recover the same server state.
- PGlite has one connection. Sequential rollback/ordering tests do not establish concurrent mixed-version/session transactions, WAL/replication or peak-load performance. Production deployment and real Android/iPhone acceptance remain separate gates.
